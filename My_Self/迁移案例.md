Sure, let me share a real case I handled for a customer who wanted to migrate their on-prem data center to Azure because their local DC contract was expiring.

Their environment had multiple core systems — including MySQL databases, web servers, and application servers — all running on-prem. We planned a lift-and-shift migration using Azure Migrate, replicating virtual machines into Azure VMs through a site-to-site VPN, and using Private Endpoints for secure replication.

During the incremental replication phase, a few MySQL servers failed with a “High Churn Issue Limit” error, meaning the target disk’s I/O rate was overloaded. That usually happens when the source server generates too many write operations — which is typical for databases or log servers.

I scheduled a remote session with the customer to do a detailed root-cause analysis.
We first confirmed the agent status with commands like ps -ef | grep walinuxagent, and restarted it using systemctl.
Then I reviewed system logs with journalctl, dmesg, and checked system performance using tools like vmstat, iostat, dstat, and free to monitor CPU, memory, and disk I/O.

The key metric we found was from iostat -dx 600 3: the write throughput was around 8 MB/s, and the average write request size was 17 KB — much higher than what their current standard disks could handle.

We suggested upgrading the Azure replica disks from Standard to Premium SSD, but the customer was very budget-sensitive — Premium storage costs roughly 4-10× more depending on the tier. They pushed back and even thought we just wanted them to pay more.

Instead of arguing, I proposed an alternative. I knew our Database Migration Service (DMS) could handle high-I/O workloads more efficiently. So I reached out to the DMS product team, explained the scenario — MySQL 5.7, 80 GB data, downtime under 15 minutes — and arranged a joint call with the customer.

Together we designed a binlog-based real-time replication with incremental cutover.
I also showed the customer a cost comparison table — using PaaS database (Azure Database for MySQL) would reduce long-term operational costs because of built-in backup, high availability, and maintenance.

I stayed on the call during the test and final migration to ensure everything went smoothly.
Eventually, the DMS migration succeeded — zero data loss, downtime under a few minutes — and the customer was really happy.
In fact, they later reopened other cases and specifically requested to work with me again.

So that project not only solved a technical bottleneck, but also improved customer trust and showed how thinking beyond tools — focusing on the customer’s business constraints — can deliver a better outcome.
